Mimo-Travel:把大模型旅行规划变成一条可执行的数据链路

发表于2026-07-12|更新于2026-07-12
|浏览量:

本文是一篇工程架构复盘，面向了解 Python、HTTP API 和大语言模型基础概念的读者。文章中的代码和结论以项目当前代码为准，同时会明确标出尚处于架构设计阶段的部分。

语言理解负责理解需求，外部 API 负责提供事实数据，运筹算法负责做可行性决策，前端负责把结果变成可交互的地图体验。

旅行规划不是文本生成问题

旅行规划最容易被低估的地方，是它看起来像一个聊天问题，实际上却是一个带有时间窗、空间距离和个人约束的决策问题。

用户说“带老人和行李，上午从虹口出发，想去几个景点，晚上六点前结束”，系统至少要处理这些事实：

  • 景点是否真实存在，坐标是否可靠；
  • 景点什么时候营业，需要停留多久；
  • 相邻地点之间到底怎么走；
  • 行李和同行人员会不会放大步行、换乘和等待的成本；
  • 当前已经消耗了多少时间、体力和注意力；
  • 这条路线能不能在现实中执行。

如果让大模型直接输出一篇攻略，它可以写出通顺的答案，却不能天然保证这些约束成立。

MiMo Travel 的做法是把问题拆开：

这也是这个项目最值得复盘的地方：它没有把“大模型更聪明”当作系统可靠性的唯一来源，而是把模型放回一个由数据、算法和协议共同组成的工程系统里。

本文的主要实现内容

  • 用 LLM + Tool Calling 构建真实业务 Agent；
  • 把外部 API 接入模型工作流；
  • 让模型输出经过确定性算法校验；
  • 为 Agent 设计流式前后端协议；
  • 在地图产品中处理路线、GeoJSON 和坐标系转换；
  • 需要区分“架构蓝图”和“当前已实现链路”。

设计蓝图：用 DAG 给 Agent 划清职责

项目根目录的 AGENTS.md 定义了更完整的多节点架构：

每个节点都有自己的输入、输出和禁止事项：

节点 角色 负责什么 不负责什么
profiler Scanner 提取行李、人数、时间窗等物理参数 不推荐景点，不寒暄
explorer Scraper 获取并清洗真实 POI 数据 不规划先后顺序
scheduler CPU 按时间窗和状态约束计算行程 不调用 LLM，不输出文本
editor Surgeon 对既有行程做局部修改 不触发全局重算
interpreter Spokesperson 解释最终排期和约束原因 不修改行程数据

这套设计的核心不是给节点起了几个漂亮的英文代号，而是建立了边界：

设计目标和当前实现不是一回事

需要诚实说明的是：这套 DAG 是项目的架构规范，但当前主入口已经演进为 LangGraph ReAct 工具链。

当前代码中已经存在并发挥作用的能力包括：

  • DualTrackProfiler：物理约束和潜在状态提取；
  • ExplorerAgent：联网搜索和 POI 结构化；
  • AdvancedOPTWScheduler：确定性行程调度；
  • AcademicTransitOptimizer：交通方式综合效用计算；
  • SSE：状态、文本和地图数据的流式传输。

但 editor、interpreter 和 route_entry 尚未以完整独立节点的形式接入当前主入口。当前版本中，部分职责由 ReAct Agent 和最终模型输出共同承担。

这不是需要掩盖的差异。对于工程项目，设计蓝图和可运行实现本来就会随着迭代发生变化。把两者分开写清楚，反而能让架构演进更可信。

为什么没有让模型直接生成一切

这个项目最重要的架构决策，也许是没有把所有工作都塞进 Prompt。

直接让 LLM 规划的方案

优点：

  • 开发快；
  • 交互自然；
  • 对模糊表达有较强的适应能力。

缺点：

  • 坐标、时间和路线容易出现幻觉；
  • 结果难以复现；
  • 很难保证营业时间约束；
  • 不容易表达体力和行李等动态状态；
  • 失败原因不容易定位。

MiMo Travel 的混合方案

优点：

  • 模型负责语言和工具编排；
  • API 提供事实数据；
  • 调度器负责可行性；
  • 前端协议稳定；
  • 每一层都可以独立调试。

代价：

  • 代码量更多；
  • 需要处理 API 限流和超时；
  • 需要维护数据契约；
  • 模型、工具和算法之间存在编排复杂度；
  • 外部 API 不可用时，用户体验会变差。

这个取舍很明确：系统牺牲了一部分“马上生成答案”的简单性，换取了更强的可检查性。

当前版本的限制

1. 完整 DAG 尚未全部接入主流程

profiler、explorer 和 scheduler 已经有对应实现或实现思路，但 editor 和 interpreter 目前还没有作为独立节点完整运行。

当前版本应该描述为：

而不是已经完成了全部 DAG 节点的生产级实现。

2. 当前路线方式选择是距离启发式

步行、公共交通和驾车的选择主要依据相邻 POI 的球面距离。它还没有把实时拥堵、天气、用户明确偏好和完整的多目标交通比较统一纳入一个全局求解器。

3. 调度器的初始坐标仍有改进空间

当前 AdvancedOPTWScheduler 的初始坐标是 (0, 0)，第一段距离并不是从真实出发地坐标开始计算。

后续应该把出发地先经过 geocoding 或 POI 搜索，再把真实坐标注入调度器。

4. 测试体系还不够完整

当前前端构建已经通过，但后端还需要补充：

  • 调度器单元测试；
  • 营业时间边界测试；
  • 行李和疲劳状态测试；
  • 高德 API mock 测试；
  • SSE 帧解析测试；
  • 前端地图点击和坐标转换测试。

这些测试会比继续堆 Prompt 更直接地提升系统可信度。

FAQ：这个项目到底是不是多智能体

当前版本使用了多少个 Agent？

当前主入口使用 LangGraph ReAct Agent，通过工具完成 POI 搜索、行程计算和天气工具调用。Profiler、Explorer 等角色已经有独立模块或设计，但还没有全部以完整 DAG 节点方式接入主流程。

为什么 Scheduler 必须和 LLM 隔离？

因为营业时间、总时长、体力消耗和候选剪枝需要稳定、可复现的计算规则。让模型自由修改这些结果，会削弱系统的可测试性。

为什么要返回 map_data，只返回 Markdown 不行吗？

Markdown 适合解释，GeoJSON 和路线 legs 适合空间展示。拆成两种数据后，文本和地图可以独立更新，也方便未来接入其他客户端。

Hexo Butterfly 能直接使用这篇文章吗？

可以。文章使用标准 Markdown、Mermaid 和图片路径占位。将图片放入 Hexo 的 source/img/ 目录，并根据你的 Butterfly 配置调整图片路径即可。

下一步：从“能规划”走向“可持续编辑”

如果继续迭代，我会优先做四件事：

  1. 把真实出发地坐标接入 Scheduler，修正第一段距离计算；
  2. 为 editor 实现局部时间窗替换，避免用户修改一个景点时全局重算；
  3. 将 interpreter 独立出来，只允许它解释已排入行程的数据；
  4. 建立一组离线 fixture，覆盖时间窗、行李、体力和 API 失败场景。

这四项工作不依赖更大的模型，却会明显提高系统的工程完整度。

总结

MiMo Travel 的核心不是“用大模型生成旅游攻略”，而是尝试建立一条可检查的数据链路：

大模型提供理解能力，外部 API 提供事实，算法提供约束，前端提供验证入口。

当这几部分被拆开之后，旅行规划就不再只是一次文本续写，而变成了一个可以调试、解释和继续演进的工程系统。
