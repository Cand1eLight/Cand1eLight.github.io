2026 年 9 月学习记录（9 月 15 日—21 日）：从 GazeShift 正式训练到 StreamNet

发表于2026-09-21|更新于2026-09-21|技术复盘
|浏览量:

记录区间：2026 年 9 月 15 日至 21 日（Asia/Hong_Kong）。

本周包括一次完整的 GazeShift 独立训练、一轮评估代码审计、StreamNet 论文精读结项，以及论文批注和组会汇报材料。文中会把我的训练结果、作者 checkpoint 结果、论文报告数字和教学练习分开；它们不是同一类证据。

这一周最密集的工作围绕两个问题展开：GazeShift 的训练流程究竟复现到了什么程度？StreamNet 的 stream buffer 到底保存了什么？

我得到了一个完整训练结果，也发现一个原本打算做的 calibration-degree sweep 完全没有改变实验条件。与此同时，StreamNet 的图和表也逼着我分清 tensor、patch 与 buffer。两件事合在一起，给我的提醒很直接：跑完任务不等于验证了问题；读懂名词也不等于能还原数据和执行过程。

9 月 15 日：重新抓准 MCUNetV2 的贡献中心

在上一轮阅读里，我一度把 MCUNetV2 概括成“把多种已有方法有机结合起来”。学长指出应该先关注运行时后，我重新对照摘要、引言贡献列表和结论，发现自己的概括确实把主次说反了。

更准确的顺序是：

  1. 核心方法： patch-by-patch 的跨层推理调度，改变 MCU 推理时计算局部区域的顺序，避免同时物化完整的早期 activation。
  2. 代价处理： patch 有重叠，可能重复计算；receptive-field redistribution 用来缓和这项代价。
  3. 自动设计： 联合搜索网络结构与推理调度，在给定任务和资源约束下挑选配置。

“运行时”在这里也要分清两个含义。一方面，它是设备实际执行推理时的顺序、张量生命周期和 buffer 复用；另一方面，runtime system 是安排 kernel、buffer 与内存的运行软件。部署前选好的 schedule 仍然会改变运行时执行，并不表示设备每遇到一个输入都动态搜索网络结构。

我还需要保留 novelty 的边界：patch 或局部跨层计算思想并非 MCUNetV2 第一次出现。不能只看到一个实现形式相似的技术，就说论文没有贡献；也不能把相关思想说成本文首创。更合适的做法是沿原文定位它具体解决的 activation bottleneck、调度范围、重算代价和联合设计。

这次修正也解释了为什么“有多个组成部分”不等于“贡献就是把模块拼起来”。分析论文时，先问主方法改变了什么，配套设计解决了主方法的什么代价，最后才讨论搜索或优化过程。

GazeShift 全数据训练：从受限子集走到正式训练管线

本周的主要实验工作是把 GazeShift 从时间受限的小样本尝试推进到全量数据训练。这里的“正式”指按更完整的数据与训练流程跑完，不表示已经与论文结果完全复现。

先审数据、官方权重和训练入口，再启动长时间任务

全量 VRGaze 数据检查得到：

数据部分 对数 图像数 备注
Train 1,112,157 pairs 2,224,314 images source/target 成对图像
Validation 132,150 pairs 264,300 images 验证数据
数据目录 — — 约 160 GB

论文文本中“约 2.1M”与本地按 pair/image 统计出来的数字不同，首先需要检查计数单位和数据表示，而不是立刻认定下载错误。

代码审计还发现右眼静态验证 metadata 中有路径拼写问题，影响 1,006 条记录；数据加载器也仍指向先前的子集 metadata。我把这些修复为全量数据路径，并把 smoke test 用于依次确认数据加载、30 维模型输出、按用户组织的 batch、五个 $K$ 值评估和 checkpoint 保存。

9 月 17 日，我先按 README 下载作者 checkpoint，并在 14:25 用本地 evaluator 测得 1.8390609°。随后我明确提出，目标是训练自己的高精度模型，争取达到或超过论文水平，当时给出的目标约为 1.83°。因此，官方权重并非训练后才被发现；独立训练也不是没有目标地重复跑一遍。

现在回看，更值得补上的决策记录是：已有 checkpoint 是否已满足演示或应用目标，以及独立训练需要多少预算、何时止损、怎样判断达到目标。后续聊天中，我曾再次说明独立训练的目标；把官方 checkpoint 说成训练后才发现，与 9 月 17 日记录不符，本文按当时记录更正。

之后我检查 checkpoint metadata，发现其中的 gaze_dim=5 与实际网络输出不一致；实际网络是 30-D。随后对照 state dict，官方与自训练模型各有 210 个 tensors，缺失、额外和 shape 不匹配均为 0。这不能解释全部精度差异，但排除了一个简单的结构不一致猜测。

正式训练之前遇到的几个真实阻塞

全量训练不是把命令贴进终端就自然开始。我遇到并处理了两类 Lightning/DDP 问题：

  • Lightning 自动替换 distributed sampler，与按受试者分组的自定义 sampler 冲突；
  • 部分 loss step 没使用模型的某些分支，标准 DDP 因 unused parameters 拒绝继续。

另外，有一条很长的训练命令曾被截断，关键 flags 没有真正进入进程。我停掉了它，没有让它按错误默认设置跑完整程。之后我开始查看真实进程参数，而不只相信复制粘贴的命令文本。

这几步让我更明确，复现的第一阶段不是“跑出数字”，而是确认数据、模型维度、采样器、实际参数和输出路径确实是自己以为的那一套。

训练结果：完整跑完，但没有达到数值复现

更新代码并完成 smoke test 后，正式 run 完成了 11 个 epoch、global step 406,650。自训练模型的最佳 calibration angular error 是 1.882109°，日志同时记录了 0.612402 的标准差。这个标准差不是置信区间，也不能据此说结果“包含”作者数字。

与训练前已经重验过的作者 checkpoint（1.8390609°）相比，自训练结果仍有差距：

相对作者 checkpoint，独立训练误差约高 2.34%。因此我能支持的结论是：自训练流水线完成了一次全数据训练，但 1.882109° 没达到训练前设定的约 1.83° 目标；作者 checkpoint 的评估值为 1.8390609°。 目前没有多 seed 分布，不能讨论差异是否有统计显著性。

在这次 run 的固定 calibration 设置下，更多个人校准样本对应更低误差。它不能说明 polynomial degree 的影响，也不能外推成所有用户或所有划分下都会有相同趋势。

一次无效的消融：degree 参数看起来变了，实际计算没变

我曾尝试比较 calibration polynomial degree 1–4。后来发现命令行参数虽然被保存，实际代码路径却把 calibration 固定成 1–4 ensemble。四次运行输出逐位相同。

这不是一个“度数影响为零”的有效实验，而是一个没有真正改变自变量的无效 sweep。它最直接的教训是：跑参数实验前，要从命令行参数追到它最终被哪个函数读取，并检查实际执行的配置。否则，重复的输出只证明代码路径没有响应，不证明理论假设。

先前一次旧 commit、旧 5-D 设置的全量 run 得到 2.411860°，也只能作为诊断性基线。它与当前 30-D 最终实现的代码路径不同，不应混在同一表里冒充本次结果或用来归因某个单独超参数。

误差差距的原因：目前是候选解释，不是结论

当前架构的 tensor 结构已对齐，但独立训练与作者 checkpoint 仍有约 0.043048° 差异。聊天记录中提出的可能来源包括：

  • source/target pair 的动态随机流与作者训练顺序不同；
  • 作者使用 strategy=auto，本地为兼容自定义 sampler 调整了单进程/DDP 路径；
  • 软件依赖和计算环境没有完全锁定。

这些都属于待验证解释。现有材料没有证明其中某一个是根因，更不能挑一个好讲的超参数，把差距全归到它上面。

作者的 exact pair sequence 与完整环境没有充分公开，当前更稳妥的下一步是保留独立训练模型作为复现证据，使用作者 checkpoint 做演示或部署路径基准，并在未来长跑前先做资产、参数和代码路径审计。官方权重已经在这次训练前验证；这次复盘的重点不是“先找权重”，而是把既有基线、独立训练目标、预算和停止条件放在同一张决策表里。

训练之后没有继续 fine-tune 的原因

我考虑过从最佳 checkpoint 用更低学习率继续训练 20K–40K steps，但这只是提议，没有运行。共享 RTX 5090 随后被其他任务占用；当时观察到约 24,025 MiB 显存使用、GPU 100% utilization、576.52 W 和 81°C。这只是一次机器状态截图，不能说成我的训练功耗测量。

所以本周没有 fine-tuning 结果、energy study 或板端部署结果。

StreamNet：stream buffer 到底是什么

9 月 19—20 日，我继续并完成了 StreamNet: Memory-Efficient Streaming Tiny Deep Learning Inference on the Microcontroller 的论文学习，规定论文清单来到 3/5。阅读中最大的障碍，是 tensor、patch 和 stream buffer 一开始很容易被当成三个近义词。

名词 在 StreamNet 语境中的意思
Tensor 完整的逻辑 feature map
Patch 当前正在计算的局部空间区域
Stream buffer 为后续 patch 保留下来的、已经算出的部分中间 activation

stream buffer 不是输入 patch，也不是某个卷积的一项乘积，更不是最终的 $Y$。例如，3×3 卷积核在一个 5×5 patch 上滑动，会产生一个 3×3 的中间输出 tile；StreamNet 暂存的是已经完整算出的中间 activation 区域，供下一 patch 复用，避免再算一次对应的整组 MAC。

这也是我后来能用自己的话复述的关键区别：buffer 保存的是已完成、可复用的局部结果，不是尚未完成的乘加碎片。

1D 和 2D stream buffer 的空间取舍

StreamNet-1D 沿一个空间方向复用中间 activation；2D 版本进一步沿另一个方向复用，也会保留角落区域的状态。2D 需要更多 SRAM，但可以减少更多重算。究竟选哪种取决于 patch 数量、切分位置、重叠量和可用 buffer，而不是“SRAM 越少，StreamNet 的价值就一定越大”这样一个单变量判断。

我在最终综合复述时有两处需要纠正：一开始低估了 2D buffer 需要的角落状态；另一次把“低 SRAM”直接等同于更高方法收益。最后把结论收回到多个因素共同决定的空间—内存—重复计算权衡。

padding bypass 跳过哪些位置

另一个容易讲错的细节是 output-padding bypass。它跳过的是输出坐标本身已确定为 padding、语义上必为零的位置；它不会跳过所有输入窗口里碰巧含有 padding 零值的有效边界输出。

这个区分看起来细，但它决定了“省掉的计算是不是合法结果”。只要有效输出仍依赖窗口中的真实输入，就不能因为窗口边缘补了零便把它整个跳过。

读 StreamNet 的实验表：公平对照与机制消融分开

论文图表中，等 SRAM 预算下与 MCUNetV2 的比较回答的是方法级结果：在相近内存预算时，延迟是否有改善。固定 n_patch 或 split_idx 的 ablation 则回答机制级贡献：改变某一个设计选项会怎样影响内存与计算。

论文的 Table 1 与 Table 3 回答的是不同问题。Table 1 的近似等 SRAM 比较只涉及 StreamNet-2D 与 MCUNetV2，是方法级结果；Table 3 在固定相同的 n_patch、split_idx 消融设定下报告 1D/2D 机制对照，几何平均 latency gain 分别约为 3.40× 和 7.28×。这两组数字不能混成“等 SRAM 时 1D/2D 都快了多少”。它们都是论文在其硬件、模型和设置下报告的数字，不是我的代码或开发板实测。MAC 减少也不能直接等同 latency 减少，因为内存搬运、buffer 管理、控制开销和未分块层仍会影响端到端时间。

截至结项，我完成的是论文机制、关键图表和综合复述；StreamNet 官方代码检查、能耗测量和真实板端复现仍未开始。

9 月 20 日：把精读变成能回到原文的批注

本周我还把两篇先前精读论文整理成可定位的批注 PDF：

  • TFLM： 对 12 页材料重新做了 44 处来源定位的高亮与批注，覆盖 Figure 4 坐标轴、scratch 内存、顺序执行多模型与并发线程的区别、BatchNorm folding、Dropout 删除，以及应看生命周期规划后的 peak memory，而不是把所有中间张量大小加总。
  • MCUNetV2： 用户发现此前一版批注对象错成了 StreamNet，而且“逐页解释”并非锚定原文的批注。随后纠正为 MCUNetV2，完成 13 页、32 处原文句子/图表定位的高亮与说明，包含运行时执行、MB1/MB6、(p/n)、supernet search，以及 Table 3 正文 16.7 与表格 16.9 的数字差异。

这次过程里确实发生了一次质量错误：论文对象选错，批注形式也偏离了要求。有效的修复方式不是把已有解释说得更长，而是核对 PDF 标题与论文列表，并把每条注释锚定到具体句子、图、表和数字上。

另外，9 月 15 日完成了一份 24 页 GazeShift 组会汇报，主要整理此前受限子集阶段的工作。页数和交付物可以记录，但其中的旧实验不能记作本周新跑出来的结果。

课程、工具和隐含假设检查

Optimization Lecture 3：本周只推进了前段

9 月 16 日，我发现手里的 Lecture 3 是扩展版 61 页；旧的“已完成约 70%”判断基于一份 33 页版本，不能沿用。随后从第 34—37 页开始学习 $L$-smoothness、凸梯度下降的收敛和步长条件。

本周记录支持的是“开始并推进到这些概念”，没有独立最终作答的证据。Line search、SGD 和 backprop 等后续主题当时还在待学范围，不能写成已掌握。

论文网页翻译助手：先保护阅读边界

我设计了一份供浏览器论文阅读使用的翻译助手提示词，并选择中文作为控制语言，因为我的主要科研阅读和推理语言是中文。要求覆盖网页中的提示注入、只选中一段文字时的处理、OCR/PDF 损坏、公式/表格/代码保留、术语一致、上下文不能凭空补造、作者原意不能被弱化，以及不能悄悄缩写内容。

这是研究阅读工具的设计稿，不是已验证的产品。它提醒我，一个论文助手不仅要“翻译得通顺”，还不能因为页面文字里含有命令，就偏离用户指定的阅读任务。

一道糖果题：先说清抽取规则

9 月 16 日的最坏情况糖果题暴露了一个隐藏前提：能否通过触摸分辨形状，并主动选择形状？如果可以根据形状主动选取，保证条件的答案是 21；如果只是完全随机取出、不能控制形状，则是 29。

这道题不属于论文研究，却很适合记录为一个通用学习习惯：解题之前先查清动作规则。相同的数量表，在“可控制选择”与“随机抽取”下，对应的是不同的最坏情况问题。

下周的具体入口

  1. 让 calibration-degree 配置真正穿过命令行、配置对象和执行函数，再做独立划分、多 seed 的 sweep；在此之前，不使用相同输出作 ablation 结论。
  2. 固定 GazeShift 的数据 pair、依赖、训练参数和 checkpoint 评估脚本，把随机过程与环境差异逐项记录；先判断什么可以重现，再解释剩余差距。
  3. 对照 StreamNet 官方代码检查论文中的 1D/2D buffer、n_patch、split_idx 和 padding bypass，先做代码级证据，再决定是否值得板端复现。
  4. 继续 Lecture 3 时把 $L$-smoothness、步长条件与收敛结论连起来，完成至少一次不看讲解的推导或题目，补上本周缺少的独立验证证据。

这周真正改变的是我对“实验完成”的定义：训练进程退出只是一个事件；只有参数真的生效、数据协议被核对、比较基线说清楚，得到的数字才有资格进入结论。
