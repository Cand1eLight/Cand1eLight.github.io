从 .tflite 到一次完整推理：我如何读懂 TensorFlow Lite Micro

沿着模型转换、算子注册、Tensor Arena、静态内存规划与执行调度，梳理 TFLM 如何在资源受限的 MCU 上完成一次推理，并结合论文图表辨析性能结论与适用边界。

阅读日期2026-09-21论文TensorFlow Lite Micro: Embedded Machine Learning on TinyML Systems领域TinyML · TensorFlow Lite Micro · MCU 推理

我第一次读 TensorFlow Lite Micro: Embedded Machine Learning on TinyML Systems 时，几乎还没有学过 MCU 推理框架。那时我大概知道模型要放进开发板，却说不清 .tflite 里面到底是什么、Interpreter 为什么叫解释器、算子如何找到 kernel，更说不清 Figure 4 里的 A、B、C、D 为什么形状不同。

后来学长追问 Figure 4，我没把坐标轴、内存大小和生命周期讲明白，这篇论文也就被打回来重读了。现在重新回看，这次卡住反而挺有价值：它逼着我把“模型格式—算子注册—内存规划—推理调度—平台优化”整条链真正连了起来。

我现在对 TFLM 的一句话理解是：

TFLM 用一个足够小、足够可移植的解释器读取 .tflite 模型，在初始化阶段完成算子绑定和固定内存规划，在每次 Invoke() 时按拓扑顺序调用已经编译好的 kernel，从而让同一套上层框架运行在缺少操作系统、动态内存和统一硬件架构的 MCU 上。

这篇论文真正想证明的也不是“TFLM 能跑神经网络”这么简单。它要证明的是：在 TinyML 中，大部分时间花在卷积、全连接等长时间运行的 kernel 上，所以解释器的调度成本可以被这些计算摊薄。这样就能用很小的运行时开销，换来模型更新、跨平台移植和厂商逐算子优化的灵活性。

我是怎么把这篇论文重新读通的

这次没有机械地从第一页逐句翻译到最后一页。我把 How to Read a Paper 的分层阅读思路和 AI 辅助结合起来：

  1. 先快速浏览摘要、章节、Figure 和 Table，弄清论文在解决什么问题、结构怎么展开，再列出真正影响理解的疑点。
  2. 我自己重点攻克这些节点：.tflite、Model Loader、OpResolver、Tensor Arena、Figure 4、Invoke()、多模型、多线程和性能表格。
  3. 让 AI 帮我定位原文、复算数字、提出反例；不同任务分开检查，最后仍回到论文图表和原句核验。我先自己解释，再区分“概念正确、措辞不精确、实质错误”，最后把整条推理路径不看答案地串起来。

我不让几个角色对同一个“创新点”自由发挥后再按多数投票，而是把证据任务分开：原图和原文核对事实，独立计算核对数字，实现细节和反例检查结论边界。角色数量本身不能保证突破，能不能把每个判断追溯到不同而可靠的证据，才是关键。

这个方法节省的是机械搜索和整理时间，没有省掉判断。让几个 AI 都回答“这篇论文有什么创新”，很容易得到相似的常见答案；让它们分别找证据、算数字、找反例，最后再对照原文，才更容易暴露分歧。比如 Table 2 的总周期和计算周期可以很快找到，但解释器开销为什么上升、正文所说的“超过 4 倍”是否和表格一致，还是要把数字亲自算一遍。

为什么 MCU 需要一套专门的推理框架

论文先总结了嵌入式机器学习面临的四类根本困难。

缺少通用软件能力

很多 MCU 没有完整操作系统、虚拟内存、文件系统和动态内存管理。有些设备甚至缺少硬件浮点。桌面软件里习以为常的能力，在这里都不能被框架默认依赖。

硬件和工具链高度碎片化

嵌入式市场没有统一到一两个主流架构。不同厂商拥有不同 ISA、DSP 扩展、IDE、编译器和私有工具链。若每块芯片都维护一套一次性的推理框架，模型迁移和优化成本会迅速失控。

SRAM、Flash、功耗与代码体积都很紧

TinyML 不只限制模型参数。运行时激活、临时工作区、解释器和算子代码都要争夺有限资源。即使应用只需要几个固定模型，固件中链接了从未调用的算子，也是在浪费 Flash。

深度学习本身还在快速变化

训练框架不断增加新算子和新网络结构。论文写作时，TensorFlow 支持 1400 多个操作，而 TensorFlow Lite 只支持约 130 个。部署框架既不能无限扩张，也不能每出现一个新模型就从头手工改写。

这些问题共同决定了 TFLM 的方向：框架只负责模型计算，把平台相关能力留给应用和硬件厂商。

论文列出的实际应用包括关键词唤醒、预测性维护、声音异常检测、视觉目标检测和人体活动识别。它们的共同点是传感器数据连续到来、设备需要长期低功耗运行，重复推理成本远比偶尔一次的初始化更重要。

四条设计原则

论文的设计不是从模块列表开始，而是先给出了四条原则。

1. 把功能范围压到最小

TFLM 假设模型、输入数组和输出数组已经位于内存中。它负责神经网络计算，不负责从文件系统加载模型，也不负责摄像头、麦克风、网络和线程调度。

这个边界让我理解了“框架”和“产品功能”的区别：TFLM 可以执行一个手势识别网络，但采集图像、触发推理、显示结果、处理中断，仍由应用或平台代码负责。

2. 让硬件厂商能够逐 kernel 优化

卷积、全连接、激活、池化和 softmax 等算子占据绝大部分计算时间。TFLM 为算子定义稳定接口，厂商可以保留解释器和模型格式，只替换某些 kernel。例如 Arm 可以接入 CMSIS-NN，而不需要重新设计一整套模型编译器。

3. 复用 TensorFlow Lite 的训练与转换生态

模型转换比想象中复杂。转换器要处理训练图到推理图的变化、量化、常量折叠、数据类型和参数范围，还要判断目标运行时是否支持每个算子。

论文在 §3.3 确实提到这件事：导出时可以把 BatchNorm 这类常量表达式折叠进固定值，并移除 Dropout 这类只在训练时有用的操作。它没有在文中推导 BatchNorm 的折叠公式，下面这组公式是我为理解“折叠进卷积”补的标准推导。

BatchNorm（批归一化）会先用均值和方差把某一层的特征值缩放到较稳定的范围，再用可学习的缩放系数 $\gamma$ 和偏移量 $\beta$ 调整回来。训练时它使用当前 batch 的统计量并更新运行统计量；推理时不再有一批训练样本可供统计，而是使用训练阶段保存的固定均值和方差。

4. 用“Bag of Files”适应不同构建系统

这个方案提高了可移植性，也留下了工程债务：论文当时的项目生成过程混合了 makefile、脚本和 Python，维护与调试并不轻松。作者在论文里直接承认了这一点。

.tflite 是怎么来的

模型先在 TensorFlow/Keras 等训练环境中产生 training graph。TensorFlow Lite Exporter 将它转换成适合推理的 inference graph，并生成 .tflite FlatBuffer。

.tflite 不是 Arm 机器码，也不是提前生成的一段卷积程序。它主要保存：

  • 按拓扑顺序排列的算子列表；
  • 输入、输出和中间张量的元数据；
  • 张量形状、数据类型和量化参数；
  • 算子参数和版本；
  • 固定权重与常量 buffer。

这里最容易混淆的是权重和中间张量。

权重在训练结束后已经确定，换一张输入图像也不会改变，所以必须保存在模型中，通常位于 Flash/ROM。中间激活由当前输入计算产生，每次推理都不同，.tflite 只保存它的形状、类型等描述，真实数值在运行时写入 SRAM 的 Tensor Arena。

我这里说的 activation，是每一层算出来、传给下一层的中间数值张量；它不是专指 ReLU 这样的 activation function。比如卷积层输出的一整块特征图，就是一个 activation tensor。

因此，中间张量不保存在 .tflite 中的首要原因不是“文件太大”，而是模型导出时根本不知道未来输入会产生什么数值。

Model Loader 为什么不需要把模型全部解包到 SRAM

TFLM 使用 FlatBuffer 序列化模型。它的访问代码是 header-only，论文称二进制 footprint 通常低于 2 kB。FlatBuffer 的关键优势是数据可以直接按既定布局读取，不必先解包成另一份完整对象。

在缺少文件系统的 MCU 上，.tflite 文件还可以转换成 C/C++ 字节数组，编译进固件。Model Loader 更接近一个指向模型字节的有类型视图：它通过偏移找到 subgraph、operator、tensor 和 buffer，而不是把整个模型复制进 SRAM。需要更新模型时，如果模型确实放在独立文件或独立 Flash 区域，就可以只替换那部分；如果它被编译进固件，能否单独更新还取决于 bootloader、Flash 分区和发布流程，未必不用重刷固件。

这也解释了权重为什么可以留在 Flash：kernel 需要时根据模型中的引用读取它们。具体能否直接从 Flash 高效访问、是否需要分块搬运，取决于芯片和 kernel 实现。

FlatBuffer 也有代价。TFLM 需要 C++11 编译器；可移植的序列化参数还要在运行时转换成 kernel 使用的结构。每个算子会多几行参数解析代码，但换来了统一模型格式和快速访问。

OpResolver：模型里的名字怎样找到真正的代码

.tflite 只说明“这里需要 Conv2D”，真正执行卷积的 C/C++ kernel 必须已经编译进固件。OpResolver 负责把模型中的 opcode、版本或 custom operator 名称映射到对应的算子注册信息和函数入口。

这里可以把两个词分开记：operator 是模型节点声明的计算类型（例如 Conv2D），kernel 是实现这项计算的函数代码。这里的 kernel 不是操作系统内核。模型决定“做什么计算”，平台优化 kernel 决定“怎样在这块芯片上做得更合适”。

如果模型包含 Conv2D，而程序没有注册 Conv2D，就无法把这个节点绑定到可调用的实现。按常见 TFLM 使用流程，这类问题会在模型准备或执行到该节点之前暴露；论文说明了 resolver 的映射职责，但没有规定某个具体版本必须在哪个 API 调用、用什么错误码报告。关键是：没有 kernel 可调用时，卷积计算本身还没有开始，不会正常算到一半才发现实现不存在。

Interpreter 到底“解释”了什么

我以前把 Interpreter 理解成“把 .tflite 转译成代码”，这个说法不准确。TFLM 的执行代码早已编译完成，Interpreter 不会现场生成 C++ 或机器码。

它解释的是模型数据：

  • 当前节点是什么算子；
  • 节点需要哪些输入、输出和参数；
  • 张量位于 Tensor Arena 的什么偏移；
  • 该调用哪个已经注册的 kernel。

整个运行过程可以分成初始化与推理两大阶段。

把论文描述的初始化阶段映射到常见实现术语，可以这样理解。论文讲的是阶段职责，不要求所有版本都用完全相同的 C++ 函数名：

阶段 主要任务 典型调用频率
init() 建立算子的持久状态 通常初始化时一次
prepare() 检查形状和参数，报告算子需要的 scratch 等内存 通常初始化时一次
invoke() 真正执行该算子的一次计算 每次模型推理都会调用

我一开始还把 Invoke() 想成“激活某个功能”或“激活 kernel 代码”。这里的 invoke 更接近“调用/执行”：它不是打开某个开关，也不是现场生成 kernel。

这里还有两层 Invoke：

  • Interpreter::Invoke() 执行整个模型一次；
  • 某个 kernel 的 invoke(context, node) 只执行当前算子一次。

应用把传感器数据写进输入张量后，调用一次 Interpreter::Invoke()。解释器循环访问已经按拓扑排序的 operator list，通过内存规划得到的 offset 找到每个节点的输入、输出和参数，再调用对应 kernel。最后一个节点完成后，控制权返回应用，应用再读取输出。

论文把这次调用设计成阻塞式：整个模型执行结束后函数才返回。MCU 可以用中断处理更紧急的任务，外部 RTOS 也可以从某个任务中调用它。

为什么一定要在运行前把内存安排好

很多 MCU 没有可靠的通用 heap。即使可以调用 malloc()，长时间反复分配和释放也会引入碎片与不可预测失败。TFLM 要求应用提供一块连续的固定大小内存，也就是 Tensor Arena。

初始化时，Interpreter 根据模型和各算子的需求从 Arena 分配全部运行内存。正常的模型调用阶段不再通过 TFLM 的机制申请新空间。若某个算子执行到一半才临时申请 1 MB，它会破坏两个核心保证：峰值内存在运行前可知，以及长时间运行不受 heap 碎片影响。

正确做法是在初始化/算子准备阶段把所需空间报告给框架，让分配器在第一次推理前完成预留。这里要区分“scratch 里的数值是临时的”和“scratch 的存储地址何时分配”：论文明确说，推理过程中需要的临时数据位于 persistent-stack allocation section（持久栈分配区）。也就是说，数值可能每次调用都会变，但对应的 Arena 空间在初始化时就已经安排好，不能把它简单等同于 Figure 4 中可按张量生命周期复用的所有 activation。

Tensor Arena 的 Head、Tail 和临时区域

论文 Figure 3 把 Arena 画成从低地址到高地址的一段连续空间。

这里的 “stack” 说的是 Tensor Arena 两端的分配方式，不是线程的函数调用栈。

  • Head 从低地址向高地址增长，承载函数期/评估期的分配；中间 activation 是后文重点复用的对象；
  • Tail 从高地址向低地址增长，承载 Interpreter 生命周期内需要保留的对象，例如模型元数据、张量描述和算子状态。论文还特别指出，推理时所需的临时数据也放在这个持久栈分配区；“scratch”描述的是用途临时，不代表它的 Arena 地址一定属于 Head；
  • 两者之间的空间可在模型准备阶段用于临时规划数据，初始化完成后重新利用。

当 Head 与 Tail 相遇或交叉时，说明 Arena 容量不足，框架报告应用级错误。中间的 temporary allocation area 是模型准备/内存规划时短暂使用的空间，准备完成后可以回收。这个结构让我意识到，“分好一块 SRAM”只是开始，真正重要的是每类数据要活多久、在哪个阶段需要。

Figure 4：我真正被打回来的地方

Figure 4 把中间张量的内存规划画成矩形装箱问题。这里必须严格按原图读轴：

  • 纵轴是 Time，向下经过 Operator #1 到 Operator #8；
  • 横轴是 Memory Size，向右表示占用更多字节；
  • 矩形的横向宽度表示 allocation size；
  • 矩形的纵向起点表示张量何时产生；
  • 矩形的纵向终点表示最后一次使用何时结束；
  • 矩形的纵向高度因此表示 lifetime；
  • 矩形的横向位置表示它被安排在 Arena 的哪段 offset。

这意味着 A、B、C、D 是 Figure 4 中不同的中间内存分配对象，通常对应中间张量，不是四个进程或四个算子。它们形状不同，是因为大小和生命周期可以同时不同。

我第一次看图时，看到 A 的矩形纵向更高，就直觉地把“看起来更长”理解成“占内存更大”，没有先确认坐标轴。论文原图标得很清楚：横轴是 Memory Size，纵轴是 Time；横向宽度才是内存大小，纵向高度才是存活时间。如果已知几个张量都是 16,384 bytes，那么它们在图中的横向宽度应该相同；谁跨过更多 operator 行，谁活得更久。A、B、C、D 是不同 allocation 的示意，不是四个线程、进程或算子。

Naive 布局为不同 allocation 依次保留互不复用的横向地址区间，整体内存接近所有宽度之和。Bin packing 会把生命周期不重叠的矩形移动到相同或部分重叠的横向 offset。例如 A 结束后，D 才开始存活，那么 D 可以复用 A 曾经占用的地址。

Memory Planner 先收集 Figure 4 这类中间 buffer allocation 的大小和生命周期，再按大小从大到小排序，将它放进第一个足够大的地址空隙；若没有空隙，就放在当前末尾。这是 first-fit decreasing 的近似策略。这里说的是可按生命周期复用的中间张量区域，不要和上一节的 scratch 混为一谈。

这个逻辑峰值也是 Arena 空间需求的下界：任意一个时刻同时活着的字节数，都必须能放得下。

我当时把“全模型所有中间张量大小加起来是 6 MB”直接和 4.2 MB SRAM 比较，然后说“总和更大也可以部署”，这个判断没有依据。总和既不能直接证明放得下，也不能直接证明放不下；关键是规划后同时存活的峰值和 Arena 里其他分配。若需要同时容纳的 activation 峰值本身就是 6 MB，而可用 SRAM 只有 4.2 MB，就不能按原样部署。

这是某一时刻同时存活的中间张量容量峰值，不是任何实现下都等于最终 Tensor Arena 大小的公式；真实 Arena 还要容纳 persistent allocation、scratch、对齐和其他框架对象，也受具体布局影响。举例说，“全模型中间张量大小加起来是 6 MB”并不能单独证明 4.2 MB SRAM 一定放不下，因为不同时存活的张量可能复用地址。相反，如果内存规划后确实需要 6 MB 的同时存活区，而可供它使用的 SRAM 只有 4.2 MB，就放不下。运行时 activation 需要反复读写，不能像固定权重那样直接当成只读 ROM 数据；把它放到外部存储或 Flash 还需要显式的数据搬运、分块执行和相应硬件支持，TFLM 不会自动替模型完成这些事。单张量太大时，才需要继续看 patch/streaming 等改变执行方式的方法。

完美装箱对任意模型很难，first-fit decreasing 不保证全局最优，但能以较小规划成本得到合理结果。TFLM 不支持动态 shape，因此初始化时已经知道张量尺寸和生命周期，可以完成这项规划。

论文也支持 offline memory planning：在主机上提前生成张量 offset，再把布局作为 FlatBuffer metadata 写进模型。这可以减少 MCU 初始化开销，并让开发者按不同 memory bank 安排数据。

原地计算为什么不能随便覆盖输入

原地计算是让输出复用输入所在的地址，减少额外 buffer。它成立至少需要两个条件：旧输入已经不会被其他算子继续使用，输出的大小、布局和 kernel 访问顺序允许覆盖。

逐元素 ReLU 是典型例子。每个输出只依赖当前位置的输入，读出 $x_i$ 后可以把 $\max(0,x_i)$ 写回同一位置。

普通 $3\times3$ 卷积不同。相邻输出会反复读取重叠的输入邻域，当前输出用过某个输入，并不代表后续输出不再需要它。若没有更细粒度的访问证明，直接覆盖会改坏未来卷积所需的数据。

因此，“输出尺寸和输入尺寸一样”不足以证明可以原地计算；判断依据是最后一次读取时间与写回顺序。

TFLM 不管理线程，为什么仍能由多个线程运行

论文把“框架负责线程调度”和“代码能否被多个线程安全调用”分开处理。

TFLM 不创建线程、不提供任务调度，也不依赖 RTOS。但这不等于模型只能单线程运行：论文明确说，只要模型相关状态保存在对应 Interpreter 和模型 Arena 中，多个独立 Interpreter 实例可以由不同 task/thread 调用，也可以运行在不同 MCU core 上。

这与 multitenancy 不同：

  • multitenancy 重点是多个模型顺序执行时复用 nonpersistent/evaluation-lifetime 区域；
  • multithreading 重点是多个独立实例能否同时执行；
  • 论文的安全性结论带有前提：模型状态不能放在 Interpreter/Arena 外部的共享状态里；同一个 Interpreter 被两个线程同时 Invoke() 是否安全，论文没有给出保证，工程上应按不安全处理，除非具体实现明确提供同步；
  • kernel 内部使用 DSP、NPU、DMA 或多核并行，又属于算子实现层。

代码可以共享，因为它是可执行内容；每个并发实例的模型状态和运行内存必须隔离或经过明确的并发安全设计。TFLM 支持的是这种组合使用方式，不负责替应用创建和管理并发任务。

平台优化：厂商真正替换的是什么

TFLM 为每个算子提供参考实现，重点是正确性和可读性。面向特定硬件构建时，平台目录中的优化源文件可以覆盖参考 kernel。例如 cmsis-nn tag 会选择 Arm CMSIS-NN 的卷积、激活、全连接、池化和 softmax 实现。

这说明 TFLM 与厂商的分工是：

  • TFLM 负责模型格式、内存规划和算子调度；
  • 厂商 kernel 负责在具体指令集、DSP 或加速器上高效完成计算；
  • 应用决定何时采集输入、何时调用模型以及如何消费输出。

厂商不是在 TFLM 里“决定模型要计算什么”。模型图已经决定计算内容，厂商主要决定这些算子在其硬件上怎样实现得更快。

解释式部署与编译式部署

TFLM 运行时读取模型数据，逐节点分派到已编译 kernel。模型结构、权重和层尺寸位于独立的 .tflite 数据区，更换模型时可以只替换该区域，只要运行时已经支持所需算子。

编译式部署会在主机端提前分析固定模型，执行图优化、算子融合和内存规划，再生成 C/C++ 或目标代码并编译进固件。STM32Cube.AI、TinyEngine、TVM、GLOW、ELL 和 uTensor 是论文相关工作中讨论的代表。

路线 运行时行为 优势 成本
Interpreter 读取模型数据并逐算子调用 kernel 模型更新和跨模型共享更灵活 保留少量解析与调度成本
Code generation 部署前把模型调用关系固化进目标程序 更容易做全图融合和专用优化 模型改变后通常重新生成、编译和发布固件

TFLM 的论点不是解释器在所有环境里都优于编译器，而是在长时间运行的 ML kernel 中，解释器分派开销相对很小。这给嵌入式推理提供了另一个合理设计点。

论文证明了什么，也留下了什么

这篇论文的证据支持三个主要结论：

  1. TFLM 能在缺少常规系统能力的 MCU/DSP 上，以固定 Arena 和小型解释器运行 int8 神经网络。
  2. 对 VWW 这类长 kernel 模型，解释器运行时开销远低于 0.1%；短模型中占比会上升到几个百分点。
  3. 平台厂商可以逐算子接入 CMSIS-NN 等优化库，在不更换模型格式与整体框架的情况下获得显著加速。

论文的实验证据覆盖 Cortex-M4、HiFi Mini DSP、VWW 和 Hotword，报告稳态推理周期和内存分解；没有系统报告冷启动、能耗、多模型并发，也没有与编译式框架做端到端同条件对比。论文还明确说 TFLM 当时不支持动态 shape。因此，它支持的结论是：在这两类硬件和所测模型上，稳态解释器开销很小；迁移到不同模型、不同加速器或不同执行路径时，仍要重新测量。

放到现在，我为什么仍然觉得它值得读

即使目标平台换成更新的 MCU、带加速器的平台或不同的离线编译器，TFLM 提出的几个系统问题仍然值得先问：

  • 模型格式如何连接训练和部署；
  • 哪些算子真的得到后端支持；
  • activation、persistent state 与 workspace 如何占用 SRAM；
  • CPU fallback 如何影响延迟与数据搬运；
  • 框架如何在硬件碎片化下保持可移植性；
  • 通用调度与平台专用 kernel 如何分工。

我还没有拿到原先设想中的 M33+A55 开发板，后续更可能使用 STM32N6570-DK。这篇论文的实验没有覆盖这些目标板，所以我会把它当作理解运行时边界的基础，而不是性能预测。下一篇按任务清单要读的是 Memory-efficient Patch-based Inference for Tiny Deep Learning：它继续追问当单个 activation 本身都难以放进片上 SRAM 时，如何改变推理执行方式。TFLM 的生命周期复用能减少“同时活着”的内存总量，却不能自动把一个过大的单张量变小。

接下来涉及 STM32N6570-DK 时，需要重新核对目标工具链和运行时究竟支持什么、哪些算子会回退到 CPU、张量布局是否要转换、workspace/DMA/synchronization 需要多少内存，以及有多少 SRAM 真正能给模型连续使用。我还没有在这块板子上复现论文实验，因此不会把 Cortex-M4 的 3.91 倍直接外推过去。

总结

TFLM 的结构可以浓缩成下面这条链：

我现在能够把这篇论文讲清楚，不是因为背住了几个类名，而是因为每个模块都能回答四个问题：它读取什么、产生什么、使用哪类内存、在初始化还是每次推理中发生。

真正容易混淆的地方也可以压缩成几句话：

  • .tflite 保存固定权重和中间张量描述，不保存输入相关的中间数值；
  • Interpreter 解释模型数据并调度 kernel，不生成目标机器码；
  • Interpreter::Invoke() 执行整个模型，算子 invoke() 只执行一个节点；
  • Figure 4 横轴是 Memory Size、纵轴是 Time，宽度表示字节数、高度表示生命周期；
  • 多模型顺序运行时，模型专属 interpreter-lifetime allocations 相加，论文允许复用的 evaluation-lifetime 区域取最大值；
  • kernel 加速主要缩短计算时间，固定解释器开销的百分比反而可能上升；
  • 论文 Table 2 的 Cortex-M4 VWW 加速约 3.91 倍，Table 3 的 VWW 总内存为 81.79 kB。

这些细节连起来以后，TFLM 就不再是一堆 API，而是一套在极小资源和碎片化硬件之间做取舍的系统设计。
