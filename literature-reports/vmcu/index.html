我以为 vMCU 只是把输入和输出放在同一块 SRAM：读懂 segment 以后

读完 TFLM、MCUNetV2 和 StreamNet，我已经知道 MCU 上推理不只是“模型参数放不放得下”。TFLM 让我开始区分权重、激活和运行时内存；MCUNetV2 通过逐 patch 执行降低前段峰值 SRAM，却引入重算；StreamNet 用 buffer 留住跨 patch 还会用到的已完成激活。接着读 vMCU: Coordinated Memory Management and Kernel Optimization for DNN Inference on MCUs，我一开始把它也归入“把输入和输出放在同一块内存”的方法。

这个概括漏掉了最难的一步：同一个输入 tensor 的不同部分，什么时候才允许被输出覆盖？普通内存规划器只看整张 tensor 是否还活着；vMCU 要把这个判断推进到 kernel 的循环内部。输入段完成最后一次读取后，输出才能安全复用它的物理地址。这里既不需要重新计算，也不改变网络权重；但原有 kernel 如果仍按输入输出互不危险重叠的假设执行，就可能在读取完成前覆盖输入，产生错误结果。

我读这篇论文时，真正卡住的不是“segment 比 tensor 小”这一句话，而是 Figure 2 的箭头、Figure 3 的公式、Figure 4/5 的循环、Figure 6 的残差生命周期，以及后面实验图表究竟证明到哪一步。这篇文章按这些问题组织，不把我的理解辅助例子写成论文结果。原文和图表以 MLSys 2024 正式论文 为准；下方图片是原论文的局部裁剪，表中重算值会注明计算口径。

一、为什么整 tensor 的生命周期太粗

论文的出发点不是 MCU 完全没有内存管理。TFLM、TinyEngine 已经会规划 tensor arena，也能在某些算子上做 in-place。In-place 指在旧值完成最后一次读取以后，让新值写到原地址。例如 ReLU 可以逐元素读旧值、计算、再写回同一位置。问题是 FC 或普通卷积会反复读取输入：某段输入对当前输出“用完了”，对后续输出却可能还没用完。把整张输入与整张输出粗暴地放在同一地址，可能不崩溃，却会算错。

论文在引言中的定义很关键：segment 的生命期取其内部元素生命期的最大值——原文短语是 “the lifetime of the segment as the maximum lifetime”。因此段内所有元素都结束最后使用，整个段才算可回收。段越小，回收时刻越精细；但管理操作也更频繁。

Table 1 为什么放在这里？作者先用 A100、Kirin 990 和 STM32F411RE 的容量数量级，把 MCU 的内存约束放到读者眼前。这不是公平的性能 benchmark：表中 storage 混合了不同类型的存储；“SW Support: None”也不能理解成 MCU 没有驱动、HAL、RTOS 或编译工具链。表格能支撑“MCU 的可用工作内存很紧”，不能直接推出某个模型的峰值、速度或能耗。

Figure 1 为什么紧跟 Table 1？Table 1 给资源约束，Figure 1 才说明浪费发生在哪里。图 (a) 中 depthwise 卷积可用整 tensor 的 in-place 优化，但一般 2D 卷积若不能整张重叠，输入和输出就分开存；图 (b) 则让输出逐段覆盖已经死亡的输入段。图 (c) 是最容易核算的 FC 例子：输入 2×3，共 6 段；输出 2×2，共 4 段。整 tensor 分配要 6+4=10 段。按照图中的输出顺序，起初还没有输入段可以释放，所以先留 1 个空槽给第一个输出；后续输入段陆续结束使用，输出逐步占用其地址，峰值成为 7 段。

这幅图证明存在一种安全调度能做到 7 段，并不是说所有 FC、卷积或任意执行顺序都能达到这个数。我后来做迁移题时也发现，除了算术上的总 SRAM，还要看 bank 分布、连续空间、DMA 可访问范围和系统保留内存；“板子写着 128 KB”不等于推理 arena 可以任意使用 128 KB。

二、Figure 2 的箭头：内存管理器和 kernel 到底怎样协同

我最初看 Figure 2 时，把 Update Segment 理解成“指向输入起始地址”，又因为 Free Segment 的箭头落在输出区域，怀疑它负责设置输出指针。重新对照图和 Section 3 后，才发现这张图把不同时间的状态叠在了一幅静态图里，箭头不能当作精确的逐指令时序来读。

图的三个虚线框分别回答三件事：Section 4 的内存管理器为输入、输出安排起始指针和 segment 布局；Section 5 的 kernel 负责按正确顺序加载、计算、写回和释放；Section 6 的编译支持帮助开发这类 kernel。右侧的 compiler 框并不表示 MCU 每次运行完 kernel 后再编译一次。论文概括 kernel 为五步：Load Segment、Compute、Update Segment、Free Segment、Boundary Check。Update 是把完成的输出写回预先证明安全的位置；Free 是确认输入段最后一次读取已经结束后的生命周期更新，不是把字节清零，也不是任意设置输出 tensor start pointer。

这正是论文说的 “coordinate memory management with kernel optimization”。内存规划器不能只把两个指针交给未经修改的普通 kernel，然后指望它自动安全地覆盖输入。kernel 必须知道分段、加载与写回顺序，内存规划器也必须据此决定起始地址。若存在异步 DMA 或 NPU 读取，循环代码执行到 Free 附近仍不足以证明硬件读完；还需要对应的完成事件或同步屏障。这是把方法移植到异构平台时必须重新核对的条件。

三、Figure 3：我怎样把公式翻译回“哪个输入还能不能被覆盖”

Section 4 一度最难读，因为 iteration domain、access matrix、mapping vector、offset 同时出现。我现在用一个 FC/GEMM 计算把它们拆开。设输入 $In$ 的形状是 $M\times K$，权重将 $K$ 个输入特征映射成 $N$ 个输出特征；$m$ 是第几行，$n$ 是第几个输出特征，$k$ 是归约维度的下标。固定 $m,n$ 后，kernel 沿 $k$ 多次乘加，才得到 $Out[m,n]$。这里的 $N$ 是输出特征数、$K$ 是输入特征数；到卷积章节，这些字母的含义还会变，不能跨图照搬。

层次 它回答的问题 这个例子
Iteration domain 哪些循环坐标合法？ $0\le m<M,\ 0\le n<N,\ 0\le k<K$
Access function / matrix 这一步逻辑上访问哪个元素？ $In[m,k]$、$Out[m,n]$
Mapping vector 多维元素怎样在内存中展平？ row-major 时 $In:mK+k$，$Out:mN+n$
Offset 输入与输出从内存池的哪里开始？ 分别加 $b{In}$、$b{Out}$

所以 iteration domain 不负责判断“算出来的数值是否合法”，而是枚举合法计算实例；access matrix 也不负责乘法，它只从 $(m,n,k)$ 取出某个 tensor 的逻辑下标。最终物理位置才由布局向量和 offset 决定。若只把输入改成 column-major，合法循环域与逻辑访问 $In[m,k]$ 都不变，输入的展平地址却从 $mK+k$ 变成 $kM+m$；相应安全约束和 offset 必须重解。这是我做迁移题时真正分清“访问哪个元素”和“它存在哪里”的一刻。

四、Figure 4–6：只改内存规划器为什么不够

Figure 4 给 FC kernel 的伪代码。外层按输出行 $m$、输出 segment 起点 $n$、输入归约 segment 起点 $k$ 遍历；内层 ki、ni 是当前 segment 内的更小计算块，下标步长分别是 KI、NI。我起初以为 ki/ni 是“又给 segment 分配一种新存储”，其实它们主要是让内层计算贴合 MCU 的向量指令宽度：外层粒度服务内存生命周期，内层粒度服务计算指令。

读这段代码时，我现在会先找两个位置：输出是在所有 $k$ 块累加完后才 RAMStore，输入是在一整行的所有 $n$ 输出块都使用完以后才 RAMFree。只完成一个输出通道块，并不代表这段输入已经死了。若把循环改成 $m\to k\to n$，当前 $k$ 段在更新完所有 $n$ 以后可以更早释放；但各输出通道跨 $k$ 的部分和必须长期保留。若有 $N$ 个 int32 累加器，典型就是约 $4N$ bytes，外加实际缓冲与对齐成本。调度变了，原 offset 约束也不能原封不动拿来用。

Figure 5 的卷积循环比 FC 更密，我曾经直接看晕。先固定形状会容易些：$In[N,H,W,C]$，卷积核 $Weight[R,S,C,K]$，输出 $Out[N,P,Q,K]$；本节的 $N$ 是 batch 数，不是 Figure 3 中的输出特征数。对一个输出空间位置 $(p,q)$，kernel 遍历卷积窗口 $(r,s)$ 与输入通道 $c$，再累计各输出通道块 $k$。图中的 RAMFree(In[n,p,q,...]) 位于 $k$ 循环之后：只有这个输入位置已经供当前及未来所需的窗口全部读取，才可以回收。它不是说当前 3×3 窗口里的九个输入位置同时失效，更不能照搬到改变 padding、stride、扫描顺序或加入残差消费者的任意卷积。

伪代码是展示思想的，不是可直接复制编译的完整实现：图中有局部下标与写回切片不一致之处，也没有展开展示尾块处理。真正判断安全性仍要回到“未来还会不会读这一段”。

Figure 6 把问题从单个算子推进到多层。左边是 $A\xrightarrow{1\times1}B\xrightarrow{3\times3\ depthwise}C\xrightarrow{1\times1}D\xrightarrow{Add}E$，还有一条 $A\to Add$ 的残差边。右边 Step 1/2/3 是连续空间位置的融合执行，不是网络中只有三层。B 的 3×3 局部窗口要 9 个 segment，C、D 各暂存 1 个，所以图示调度的附加 workspace 是 $9+1+1=11$ 个 segment；这不是 11 bytes，也不是任意模型的固定峰值。

我做过一道把 3×3 depthwise 改为 5×5、同时取消残差的迁移题：在图示的同一 segment 粒度下，B 窗口变成 25 段，若 C、D 仍各 1 段，局部 workspace 变成 27 段；第一层已经完成对某个 A 段的全部读取、生成所需 B 后，该 A 段就可以释放。当时讲解一度把已取消的残差偷偷加回题设，误说我不能释放 A。这个纠正很重要：有无 $A\to Add$，就是生命周期判断的关键条件。回到原 Figure 6，Add 还要读取 A，A 就必须继续存活，直到这条残差使用完成。

局部融合还有一个经常被一句“省一半”掩盖的区别：单层若只是把分别存放的输入 $I$ 和输出 $O$ 理想地重叠，节省比例上限是 $\min(I,O)/(I+O)\le50\%$；多层融合还可能避免 B/C/D 整张中间特征图物化，因此整个模块相对非融合基线的节省可以超过 50%。Segment 越小越容易提前回收，却增加加载、地址回绕和控制开销；论文给 FC 与卷积的段尺寸选择是启发式，不是对所有平台的全局最优证明。

五、Python、C++ 和 MCU：编译支持到底发生在哪里

看到论文说 Python interface 时，我疑惑过：TFLM 主要是 C/C++，难道 vMCU 要在 MCU 上运行 Python？答案不是。Python 是主机端写 segment-aware kernel 的描述接口；它调用 RAMLoad、RAMStore、RAMFree、Dot 等 intrinsic 形成中间表示，再生成低层 C++，经 ARM 编译器生成 MCU 上运行的原生二进制。Intrinsic 也不是“IR 之后的独立运行阶段”，而是描述中可被后端降低的操作。

论文正文说有六类 intrinsic，实际逐项列出的是七个：RegAlloc、RAMLoad、FlashLoad、Dot、RAMStore、RAMFree、Broadcast。它细说了 Dot 如何结合 ARM DSP 指令、RAMLoad 如何落到内存复制、Broadcast 如何配合量化运算；不能仅凭 RegAlloc 的名字保证整个 buffer 真待在物理寄存器里。用 Python 的理由是让 kernel 作者能描述循环和分段语义、由后端统一生成目标代码，而不是宣称 C++ 本身写不出来。

这也解释了为什么“把 ARM C++ 换个编译器重编”不足以移植 vMCU：目标芯片的向量/DSP 指令、intrinsic lowering、tile 大小、对齐、交叉编译与部署链都要适配；最要紧的是重新验证每次覆盖前的最后读取条件。高层生命周期思想可借鉴，具体 kernel 不能不改就套到另一 ISA、NPU 或 DMA 路径上。

六、Table 2 与 Figure 7–8：单层实验到底比较了什么

Table 2 是配置表，不是成绩表。H/W 是输入高宽，C_in→C_mid→C_out 是输入、中间、输出通道，R/S 是 depthwise 卷积核大小，strides 是三个卷积的步长。S 组属于 MCUNet-5fps-VWW，B 组属于 MCUNet-320KB-ImageNet。它帮助解释后面柱状图为什么不同模块占用不同，但不能用其中的形状直接读出性能。S3 的 $C{in}=24,C{out}=16$，也提醒我 Figure 6 的直接残差 Add 不能无条件套到 Table 2 每一行。论文称最后的 B18 因 7×7 核大于 6×6 输入而排除，但已列入的 B16 也是 $H/W=6,R/S=7$；单凭表中这两项，排除理由并不完整。

Figure 7 先单独检验内存：九个 1×1 pointwise 卷积，在 128 KB SRAM 的 STM32F411RE 上，vMCU 相对 TinyEngine 的 RAM 降低 12.01%–49.45%；图中 case 1、2、4 的 TinyEngine 柱越过 128 KB 限制，而 vMCU 落在限制内。Pointwise 虽然空间上只看一个像素位置，却会把该位置的 $C$ 个输入通道通过权重混合为 $K$ 个输出通道，不是“每个元素互不相干”。这也是输入段可能要被多个输出通道重复读取、不能随便覆盖的原因。作者没有拿 depthwise 当作这组单层的重点，因为 TinyEngine 已有相应 in-place 优化。

Figure 8 换到 STM32F767ZI 测每张图像的能耗和延迟：柱状图左轴是 mJ，折线右轴是 ms。作者报告能耗降低 20.6%–53.0%，延迟降低 18.5%–40.0%。能耗不是“电流乘电压”本身，那是瞬时功率 $P(t)=V(t)I(t)$；一次推理的能量是 $E=\int P(t)\,dt$。论文未交代详细电流采样、供电边界和 idle 扣除方法，读者不能仅靠正文复算图中 mJ。

更重要的是，这张图不构成“只换 segment 内存管理，能耗就下降这么多”的干净消融。作者明确说 TinyEngine 对 pointwise 仍做不必要的 im2col 预处理，vMCU 还采用更充分的内层循环展开。这些实现差异也会改变 RAM 访问、时间和能耗。Figure 7–8 支持这两套完整实现的比较，不能把每一个百分点都分给 segment 复用。

七、Figure 9–12 与 Table 3：模块峰值、速度和更大模型空间

Figure 9 看 MCUNet-5fps-VWW 的 S1–S8 模块。HMCOS、TinyEngine、vMCU 各自的最大模块 RAM 分别是 48.8、36.0、13.9 KB。论文结论中的“降低 61.5% 内存瓶颈”对应 $36.0\to13.9$ KB、相对 TinyEngine 的这组峰值，不是所有网络平均降低 61.5%，也不能把每根模块柱相加当作整网运行时占用。HMCOS 主要优化图级算子调度，TinyEngine 有 depthwise in-place；三者比较的机制边界并不一样。

Table 3 回答“省 SRAM 是否一定变慢”。把表中八个 S 模块延迟相加，TinyEngine 为 245 ms，vMCU 为 238 ms；$245/238\approx1.03$，即这组模块总时间口径下 vMCU 约有 1.03× 的速度，而非延迟多了 1.03 倍。但 S6 是 20 ms 对 19 ms，vMCU 局部更慢，所以不是每一层都赢。表中的 throughput 是按单个模块的时延换算，不能直接叫作整网 FPS。

Figure 10 换到更大的 MCUNet-320KB-ImageNet。正文报告 HMCOS、TinyEngine、vMCU 峰值分别是 464.6、247.8、102.7 KB，按 TinyEngine 到 vMCU 的峰值算下降约 58.6%。这里有一个我读图时不能略过的缝隙：图里的 TinyEngine 蓝峰值线和 B2 蓝柱按刻度看接近 268 KB，与正文的 247.8 KB 不吻合；58.6% 是按正文数值计算的，不应假装图文完全一致。此图的实测板是 512 KB SRAM 的 F767ZI；作者据 102.7 KB 声称可落在 128 KB 的 F411RE，完整部署还需核对该板可用 arena、代码和系统开销，不能把图名改写成“已在 F411RE 实测”。

我最初不明白 Figure 11/12 为什么突然测图像尺寸和通道数。前面的图证明省内存，后两图则追问“这块省下来的 SRAM 能换来什么设计空间”。蓝柱把 TinyEngine 在同一 RAM 预算下的配置规范为 1×，红柱表示 vMCU 对各 S 模块允许的扩大倍数：高、宽各 1.29–2.58×；输入、输出通道各 1.26–3.17×。原文谨慎地写 “potentially increased by retraining”：重新训练后，准确率可能提高。图本身没有部署这些扩大后的整网，更没有新模型的 accuracy 表。

两张图也不是“vMCU 已经比 TinyEngine 跑了 2.58 倍大的整个网络”。每根柱对应一个模块的一条搜索轴；单模块的最大值不能同时套给整张网络。若高、宽各扩大 $r$ 倍，像素位置大约增加 $r^2$；若 pointwise 的输入和输出通道都扩大 $r$ 倍，该层 MAC 也大约增加 $r^2$。模型能放下只是一个约束被放松，还要重新检查层间形状、Flash、延迟、能耗和训练后的准确率。这是 vMCU 的系统价值，也是它还没有替作者证明的部分。

八、把 Related Work 和结论放回我的研究问题

Section 8 把相关工作分成手写 MCU kernel 库、编译器、模型重设计和 tensor-level 内存调度。CMSIS-NN、CMix-NN 等关注低位宽与高效算子；TinyEngine 还有代码生成和部分 in-place；MCUNet/MCUNetV2 通过模型搜索或 patch 执行处理预算；Serenity、HMCOS 则偏向图级算子顺序与 tensor 生命周期。vMCU 要强调的空隙是：即使整网算子顺序固定，一个 kernel 内部仍有输入段先后死亡的时间差。把这个时间差利用起来，需要内存规划与 kernel 一起设计。这里的对比是方法侧重点，不表示其他库“完全不考虑 RAM”，也不表示所有图级调度在线性网络里毫无作用。

Section 9 重复了单层 RAM 下降约 12.0%–49.5%、能耗下降 20.6%–53.0%，以及上述 VWW 峰值下降 61.5%。我现在会把它们念成带对象的结论：哪些算子、哪块板、相对谁、测了什么。vMCU 主要验证的是 dense int8、连续 row-major segment、FC、2D 卷积和倒残差模块；它的数学表达可以启发其他算子，但不能自动等同于稀疏布局、任意分支图或异步 NPU 已可直接使用。论文也没有提供端到端 accuracy 复测来证明“完全不改模型参数”在所有部署路径上都已逐项验过；Figure 11/12 更不提供更大模型的训练精度。

我最后能怎么向别人解释 vMCU

如果学长再问“这篇论文到底做了什么”，我不会只说“让 tensor 共享内存”。我会这样回答：

vMCU 把 MCU 推理中的输入激活按 kernel 的访问模式切成 segment；内存规划器安排允许部分重叠的起始地址，kernel 按确定的加载、计算、写回、释放顺序运行，使输出只覆盖已完成最后使用的输入段。单层可减少输入/输出同时驻留，多层融合还可避免部分整张中间激活物化。代价是 kernel 与内存管理强耦合，换执行顺序、硬件后端或异步访问路径都要重做安全验证。论文在特定 ARM MCU、算子与网络模块上展示了 SRAM、能耗和延迟收益；更大网络的精度收益仍是下一步机会，不是既成实验结果。

这次阅读也让我改变了检查系统论文的方式：先问数据何时最后一次被读，再看谁保证下一次写不会越界或覆盖活数据，最后逐张图核对硬件、基线、指标和分母。我已经走完了论文的 Section 1–9，并读过 Table 1–3、Figure 1–12；但“读完并能解释”还不是代码复现，也不等于所有迁移情况都已独立证明。下一步若把这条思路带到自己的 MCU/NPU 平台，我会先画真实的数据依赖和完成事件，再量化可复用的 SRAM 与额外 kernel 成本。
