把整张特征图拆开算：我如何读懂 MCUNetV2

围绕逐 patch 跨层执行、重叠计算的代价、感受野重分配与架构/调度联合搜索，梳理论文如何降低 MCU 推理的峰值激活内存，并区分解析估计、开发板测量与数据集实验结论。

阅读日期2026-09-20论文MCUNetV2: Memory-Efficient Patch-based Inference for Tiny Deep Learning领域TinyML · Patch-based Inference · MCU 内存优化

我第一次看 MCUNetV2: Memory-Efficient Patch-based Inference for Tiny Deep Learning 时，把它说成“把好几种已有方法有机结合起来”。这个概括不算全错，但没有抓住主次。学长提醒我多看运行时后，我才慢慢把中心收窄：这篇论文的核心是改变 CNN 前段的推理调度，把原本整层执行的高内存计算改成逐 patch 跨层执行。

后面的设计围绕这个核心展开：逐 patch 执行降低同时驻留的激活，却会因为 patch 输入重叠而重复计算；感受野重分配用来缓解这项代价；架构与调度的联合搜索用来寻找满足硬件预算的组合。它不是“发明了一个全新的 CNN”，也不能简化成“只做了分块、其他都不重要”。

我读这篇论文时真正卡住的问题包括：前几层为什么特别占内存？patch 为什么必须重叠？感受野是卷积核大小吗？Figure 4 里的 MB6、MB1 是什么？NAS 是不是 MCU 每次收到图像后才运行？Table 里的 MACs、SRAM、latency 和 accuracy 又分别能证明什么？这篇文章按这些问题展开，尽量把论文主张、我的理解、教学例子和实验数字分开。

论文正文和补充材料以 NeurIPS 2021 正式论文 PDF 与官方补充材料 为准。文中的表格是我根据论文数字重新排成 Markdown，不是开发板实测记录。

先把论文要解决的瓶颈说清楚

MCU 上的模型部署不能只看模型文件有多大。至少要分开看四类东西：

资源 是什么 常见存放位置 会不会随输入变化
权重 训练得到的卷积核、偏置等参数 Flash / ROM 不会
激活值 当前输入经过各层后产生的中间特征图 SRAM 会
临时工作区 算子执行所需的部分权重、im2col 等 buffer SRAM 或平台指定区域 执行期间使用
程序与运行状态 kernel、推理调度代码、张量描述等 代码多在 Flash，状态依实现而定 一部分会变化

MCUNetV2 主要瞄准的是 peak activation memory，峰值激活内存。权重已经量化成 int8，并不代表运行时的输入和输出激活一定放得下。卷积某一层运行时，输入与输出 buffer 可能需要同时存在；如果单层要用的中间张量太大，整张量生命周期规划也不能把它变小。

为什么前几层的特征图更容易成为峰值

常见层级 CNN 会逐 stage 降低特征图的空间分辨率，同时增加通道数。若高度 (H) 和宽度 (W) 各减半，通道数 (C) 加倍，那么激活元素数量会变成：

空间像素数减少到四分之一，通道数只增加一倍，所以总元素数反而减半。重复经过这样的 stage 后，网络后段的特征图通常比开头小得多。这个趋势适用于很多常见层级 CNN，但不是“所有网络都必然如此”的定理；带复杂分支或特殊算子的网络还要单独分析。

论文的 MobileNetV2 案例中，前 5 个 block 的 peak memory 超过约 450 kB，后面 13 个 block 的需求则能落在 256 kB MCU 的预算内。最高峰达到 1372 kB，远高于后段。于是作者问的不是“能不能把整个网络都再缩小一点”，而是：前段占用很高的完整 feature map，有没有必要一次性全部算出并保存在 SRAM？

论文给了一个更直接的例子。输入分辨率 (224\times224)，第一层从 3 个通道卷积到 32 个通道，stride 为 2，int8 每个元素按 1 byte 算：

输入与输出同时占用就约 539 KiB，还没算 kernel 临时 buffer、框架状态和对齐。只要可用 SRAM 预算是 256 KiB，这种逐层执行方式就装不下这一层的整张输入与输出。

  • 图中横轴是 MobileNetV2 的 block index，纵轴是 int8 条件下的 memory usage（kB）；蓝色柱是 per-layer，黄色柱是 per-patch。虚线水平线标出 256 kB 约束；标注指出 per-layer peak 为 1372 kB，4×4 patch 的 per-patch peak 为 172 kB，约低 8 倍。前五个 block 是瓶颈区，后面区段需求小。图注特别说明两种设置的网络结构和 accuracy 没变，所以这是执行调度改变带来的内存差异，不是换了一个更小模型。

Figure 1 为什么画成逐 block 柱状图？因为论文要让读者先看到“内存并不是均匀分布在整张网络里”：高峰集中在开头。只有这个现象成立，跳过“为前几层缩小整个网络”的方案才有动机。图支持的是 MobileNetV2 案例中峰值集中在早期、逐 patch 能显著降峰值；它本身还不能证明所有 CNN、所有硬件都有 8 倍收益。

为什么不能只把输入分辨率降下来

降分辨率确实能减少 (H\times W\times C)，但检测任务也会失去空间细节。Figure 2 把 ImageNet Top-1 和 Pascal VOC mAP 随输入分辨率变化的趋势放在一起，作者想说明检测性能对分辨率下降更敏感。

  • 横轴 Image Resolution、纵轴 Accuracy/mAP (%)、VOC mAP 与 ImgNet Top-1 图例，以及 “larger degrade” 标注。图中两条曲线来自不同任务和不同指标，能比较各自随分辨率变化的趋势，不能把 Top-1 与 mAP 的绝对数值当成同一种量直接比较。

我当时提出过一个很好的审稿问题：mAP 是跨类别聚合的指标，整体曲线接近并不能说明每个类别、每种目标尺寸的能力都一样。要证明大目标比小目标稳定，应该按目标尺寸进一步报告 AP({small})、AP({medium})、AP(_{large})，或做相应分组分析；Figure 2 没有提供这些分组，所以它不能单独支持这个更细的结论。

我还核对过 Figure 2 的刻度版本：我当时使用的阅读版第三个刻度是 288，而最终 PDF 的同一位置显示 228。博客引用以正式 PDF 为准，但不能只凭曲线猜作者本来想写哪个数字。这种图中文字差异要记录，不应自行“修正”成看起来更合理的值。

核心运行时方法：per-layer 改成前段 per-patch

Per-layer inference（逐层推理）是常见执行方式：完整执行一层，产生完整输出 feature map；再把整张输出交给下一层。它便于使用 im2col、tiling 等成熟卷积优化，但前段每层的输入和输出整张图都可能很大。

Patch-by-patch inference（逐 patch 推理）改变的是前段的执行顺序：一次只计算一块空间区域，让这块局部中间结果继续通过前段后续层；然后再处理下一块。等前段高分辨率部分处理完、feature map 已经较小，后段就恢复逐层执行。

我曾用一句话确认自己的理解：“不是从 X 到完整 B 再到完整 Y；而是 X 的一部分先卷积成 B 的一部分，再继续卷积成最终 C 的一部分。”这个主线是对的。补充两个边界后就更精确：第一，分块只用在网络前段，不要求整个模型都 patch 化；第二，最终输出 patch 可以各写一次，但它们依赖的输入 patch 往往要重叠，不能把需要的邻域直接删掉。

  • 图分成 (a) Per-layer computation (executing first conv) 与 (b) Per-patch computation (executing first patch)。图例逐项说明：深蓝 In memory、浅蓝 Not in memory、实线箭头 Currently executing、虚线箭头 To be executed、斜线区域 Overlapped。块上 H/W/C 标出张量空间与通道维度；conv1 s=1 和 conv2 s=2 分别表示第一、第二卷积及其 stride。左图说明完整输入/输出激活同时驻留会形成大峰值；右图说明当前只处理一个 patch，后续 patch 留待执行。

Figure 3 的一个关键细节是：per-patch 仍要有空间存放前段最后的输出 feature map，然后把每块算出的最终输出写到对应区域。它不是“SRAM 里永远只有一个 patch、其他结果全都不存在”。省下来的主要是前段中间层的整张高分辨率 activation；最后输出通常已经经过下采样，尺寸小一些。论文还提到，原始图像可由 JPEG 等压缩格式局部解码，这是输入管线允许时的额外节省，并非所有传感器输入都自动具备。

输出不重叠，为什么输入却要重叠

卷积的输出依赖输入邻域。两个输出区域虽然可以不重叠，但靠近分界处的输出仍然会用到分界另一侧的输入。如果输入 patch 只按输出区域整齐切开、把邻居像素删掉，边缘位置会缺失原始卷积需要的上下文，结果就不再等于整图逐层计算。

因此，patch 输入要带一圈 halo（边界外扩区）。相邻输入 patch 的 halo 会重叠，某些中间卷积结果便会被重复算；每个最终输出位置仍然只写入一次。内存省下来的原因是局部数据分次驻留，而不是丢弃必需的邻域信息。

论文的 MobileNetV2 例子能看出差别：224 输入切成 (4\times4)，只按几何划分时每块边长是 (224/4=56)；考虑前段累计感受野后，实际输入 patch 需要 (75\times75)。多出的部分就是 halo 和重叠所需的空间。

逐 patch 共执行 (3\times4=12) 次中间单元计算；若完整逐层只计算 B0 到 B7，则是 8 次，因此这个玩具例子多了 4 次。B2/B3、B4/B5 是重叠依赖导致的重复部分。这个计数假设每个单元的成本相同，只用于理解“重复在哪里”；不能拿 12/8 直接当论文网络的 MACs 倍率。最后输出 Y 的各个区域仍然只生成一次，不应该把 Y 的重复写入算进去。

这也解释了一个常见误区：SRAM 降 8 倍不代表推理快 8 倍。 内存占用、MACs、真实 latency、能耗是不同指标。patch 重叠会增加计算；分块还可能降低某些 kernel 的硬件利用率，所以延迟可能上升，也可能因模型和硬件不同而变化。

感受野不是卷积核：为什么要把它往后重分配

我曾问“感受野是不是卷积核大小？把 (5\times5) 改成 (1\times1) 是不是就缩小感受野？”更准确的回答是：卷积核大小决定单层看多大的局部邻域；网络某一层的累计感受野取决于一路经过的卷积核、stride 和前面层的空间跳距。 所以，一个 (5\times5) kernel 确实会比 (1\times1) kernel 在该层引入更大的局部范围，但不能把整张网络的感受野等同于某个单独卷积核。

对于普通卷积，累计感受野可用一个简化递推式理解。令初始感受野 (R_0=1)，相邻特征点映射回输入的间距 (J_0=1)，第 (l) 层 kernel 为 (k_l)、stride 为 (s_l)：

这是帮助理解的通用推导，不是论文专门提出的公式。比如连续三个 stride-1 的 (3\times3) 卷积，感受野从 1 扩成 3、5、7；前面若出现 stride 2，后续 kernel 对原图感受野的增量也会更大。

前段 patch stage 的累计感受野越大，每个最终输出区域需要的输入 halo 越宽；halo 越宽，patch 间重复计算越多。作者于是提出 receptive-field redistribution（感受野重分配）：

  • patch 执行的前段用较小 kernel、减少部分 block，让重复执行的区域 RF 更小；
  • per-layer 的后段增加 block 或较大的 kernel，把一部分感受野与计算放到只执行一遍的区域。

后段“补回感受野”是方向正确的直觉，但不表示它能逐点恢复前段没有计算出的全部信息。网络结构变了，训练后是否保住任务性能必须由实验验证。论文报告的是 MbV2-RD 在 ImageNet 和 Pascal VOC 上达到相近表现，同时降低了 patch 重叠计算；它不是数学上保证所有任务无损。

  • 图上下两行比较 MbV2 与 MbV2-RD；横向是从网络前段到后段的 block 顺序。左侧标出 large peak memory / per-patch，表示高内存前段使用 patch；右侧是 small peak memory / per-layer，表示后段恢复逐层。箭头 Reduce Receptive Field 指向前段，Increase Receptive Field 指向后段；虚线边框表示 stride=2。

    图里的 MB{expansion ratio} {kernel size} 不是 block 编号。MB6 3×3 表示 expansion ratio 为 6、depthwise kernel 为 3×3 的 mobile inverted block；MB1 1×1 表示 expansion ratio 为 1、kernel 为 1×1，不是“第 1 个 block”。Inverted bottleneck 通常先用 pointwise 卷积扩展通道，再做 depthwise spatial convolution，最后投影回输出通道；expansion ratio 描述中间通道相对输入通道的扩张倍数。图里少量 MB1 1×1、较小 kernel 以及减少的前段 block 都服务于缩小 patch stage 的累计 RF。具体模块颜色用于区分图中标出的执行区段；解释时应以图上阶段文字和箭头为依据，不额外猜颜色含义。

表里的 +3% 是 MbV2-RD 使用 per-patch 调度时，相对于MbV2-RD 自己逐层执行的 MACs 增量：

它不是精度增加 3%，也不是 latency 提速 3%。同一行中 MbV2-RD 的 patch-stage 额外计算为 +18%，但它只占全网一部分，故摊到全网是 +3%。这是“局部开销”和“全网开销”两种不同分母。

两种结构的 peak SRAM 都从 1372 kB 降到 172 kB，约 8 倍；MbV2-RD 把 patch 从 75×75 缩到 63×63，全网额外 MACs 从 10% 降到 3%，Top-1 与 mAP 数字接近。最能支持的结论是：对这个网络与任务，重分配降低了分块重算开销而没有观察到明显精度损失。表格并不能保证别的网络也得到同样 3%。

联合搜索：哪些东西被搜索，为什么需要 supernet

手工重排 MobileNetV2 可以解释机制，但不同数据集、硬件和 SRAM/Flash/latency 预算不一样。一个分辨率更高、通道更宽的结构可能更准，却不满足 SRAM；更多 patch 可以继续降峰值，却会放大重算。作者把网络结构与推理调度放进同一搜索空间。

搜索侧 符号 含义与候选值
网络结构 (k) 各 separable-convolution block 的 kernel size：3、5、7
网络结构 (e) inverted residual block 的 expansion ratio：3、4、6
网络结构 (d) 每个 stage 的 block 数：2、3、4
网络结构 (w) 每个 block 的 width multiplier：0.5、0.75、1.0
网络结构 (r) 输入分辨率：96、128、160、192、224、256
执行调度 (p) 每个方向的 patch 数；总 patch 数为 (p\times p)，候选 1、2、3、4
执行调度 (n) 前多少个 layer/block 采用 patch-based，剩下的恢复 per-layer

搜索目标可以写成：在 SRAM、Flash 和 latency 都满足预算的候选中，找验证精度最高的网络—调度组合。这个说法表示搜索目标，不表示进化算法保证找到整个巨大空间的全局最优解。

我当时问过：supernet 是什么？为什么有了它就“能搜”出合适网络？可以先把它理解成一个包含很多较小候选网络的共享权重网络。每个候选子网从 supernet 中选取一部分通道、block 或 kernel 配置，继承对应权重来快速评估，不需要每个候选都从零训练。共享权重让候选筛选可负担，但候选排序是近似评估，不等于每个候选完整训练后的最终成绩；选出的模型还要微调与量化训练。

论文把搜索过程放在部署前的训练/主机端：

这里的 runtime inference（运行时推理）不是每张图像来了之后都重新跑 NAS。搜索完成后，设备获得选定模型、权重和执行配置；MCU 对每个输入按这个固定网络与 patch 调度完成计算。运行时改变的是“每次推理怎样执行”，搜索则在部署前完成。

阶段 论文报告的做法 为什么这么做
最大网络训练 MnasNet-alike 搜索空间；ImageNet 150 epochs、VWW 30 epochs；SGD、batch size 1024、初始学习率 0.2、weight decay (4\times10^{-5})、cosine decay 先给搜索空间中的候选提供训练权重

进化搜索 population 100；每代保留 top-20；crossover 生成 50 个、mutation 生成 50 个；mutation rate 0.1，共 30 轮 在离散候选中反复筛选、组合和扰动
最终训练与部署 搜索选出的子网用初始学习率的 1/10 微调 10 epochs；int8 部署前做 10 epochs quantization-aware training 让最终子网和低精度部署条件适配

进化搜索不是“随便试到一个看起来不错的”。约束先排除装不进 SRAM/Flash 或 latency 超限的候选，验证集精度用于排序；交叉和变异产生下一代。它比穷举便宜，但仍依赖搜索空间、共享权重评估和验证设置，所以论文的“最优”应理解为在该搜索过程和候选空间里找到的最佳可行方案。

作者还解释了为什么将 width multiplier (w) 和分辨率 (r) 放进搜索空间：任务可能更需要高分辨率，而不是更宽的网络；两者直接参与搜索，比先固定好 (w,r) 再搜索 block 更灵活。MobileNetV3 的 Swish 激活在作者当时的 MCU int8 部署路径上更难量化，因此论文采用与 MnasNet、MCUNet 更接近的搜索空间。这个选择反映的是部署可行性，不是说 MobileNetV3 对所有平台都不好。

实验先分口径：解析估计与板端测量不是同一回事

论文的实验分成两种 memory profiling：

  • Analytical profiling（解析内存估计）：按模型结构统计同时需要的输入、输出激活；遇到 residual 等多分支时计算同时存活的分支，共用输入只算一次。作者假设权重可从 Flash 分块读取，因此这个口径主要衡量 activation peak。
  • On-device profiling（板端实测）：在真实推理引擎上测 SRAM 和 Flash，还包含部分权重、im2col 等临时 buffer，因此通常比解析估计更高。

  • 左图 (a) Peak Memory (kB) 比较五种网络的逐层与 4×4 patch 峰值；右图 (b) Computation (M MACs) 比较计算量，并用 +3%、+8%、+10%、+15%、+17% 标出对应开销。所有模型都使用 224×224 输入和 int8 分析。图的左右两幅分别回答“省了多少峰值内存”和“付出多少计算”，不能只保留左图后就说系统整体更好。

Figure 5 的范围是五种既有网络：MbV2、MbV2-RD、OFA-CPU、MnasNet、FBNet-A。4×4 patch 下解析峰值下降 3.7–8.0 倍；各模型开销不同，普通配置大约 8–17%，MbV2-RD 为 +3%。MnasNet 前段较大的卷积核导致更大的累计 RF 和 patch 重叠，所以开销更高。图支持“方法适用于不止一个 MobileNetV2 结构”，但仍不是对所有网络类型的证明。


  • 图例是 Per-layer (w/ TinyEngine)、Per-patch (2×2)、Per-patch (3×3)；网络标签旁的 (w)、(r) 表示 width multiplier 与输入分辨率。作者在 STM32F746 的 320 kB SRAM / 1 MB Flash 约束下，为了放得下会缩小 width 和 resolution。因此 Figure 6 反映可部署配置的板端权衡，不是只改变调度、其余完全固定的纯消融。

板端结果中，patch 执行测得 SRAM 大约降低 4–6 倍；但 latency overhead 因网络而异。MbV2-RD 的逐层 latency 是约 540 ms，2×2 和 3×3 patch 分别约 562、564 ms，增加约 4%；原始 MbV2 从约 617 ms 增到约 711、741 ms，开销更大。作者指出 patch stage 的硬件利用率可能更差，所以 MACs 增长比例不等于 latency 增长比例。

这正好回应了我自己的判断：如果设备内存已经满足、任务又优先低 latency，就不必为了追求更低 SRAM 强行采用会增加延迟的方案。方法是否值得用，要先看真正的瓶颈和任务目标。

(p) 和 (n) 不是越大越好

patch 调度里两个重要变量是：(p)，每个方向分成多少个 patch、总数为 (p^2)；(n)，前多少个网络 block/layer 采用 patch-based，后段恢复 per-layer。

  • 图 (a) 的横轴一组是 patch-based block 数 (n)，用 (p=4) 固定，左纵轴看 peak memory，右纵轴看 patch size；曲线显示 (n) 增大时，峰值先降后升，而 patch size 会因累计 RF 增大而扩张。中间图固定 (n=5)，横轴 (p) 逐渐增大，峰值内存下降。右图 (b) 以 (p) 为横轴、computation overhead 为纵轴，比较 MbV2 与 MbV2-RD；patch 越多，重叠开销通常越高，重分配可压低它。

对 MobileNetV2，论文选 (n^=5,p^=4)：前五个 block 采用 patch 推理，输入图切成 4×4 共 16 个 patch。(n) 太小，可能还没绕过最初峰值；(n) 太大，RF 和 halo 增长会把 patch 再撑大，峰值反而回升。固定 (n) 后增加 (p) 可以缩小单块工作区，但边界数量更多、重复计算也更多。因此搜索要选可行且代价合适的组合，不是把 patch 数开到最大。

为什么不直接用不重叠 patch 或其他省内存方法

最直观的办法是把输入切成不重叠区域。它没有 halo，也没有重算，却会切断 patch 边界的信息传播，改变卷积网络原有的空间关系。论文 Table 5 用 MobileNetV2 对照了这种做法、RNNPool 和 MbV2-RD：

模型 执行方式 保持推理不变性 Peak memory（fp32） 训练时间 ImageNet Top-1 VOC mAP
MbV2 Per-layer ✓ 2.29 MB 1.0× 72.2% 75.4%
Non-overlap Per-patch ✗ 0.19 MB 1.0× 71.8% 73.9%
MbV2-RNNPool Streaming ✗ 0.24 MB 3.2× 70.1% 71.0%
MbV2-RD Per-patch ✓ 0.19 MB 1.0× 72.1% 75.7%

这个表让“为什么要带 halo”更具体：不重叠 patch 内存很低，但 VOC mAP 从 75.4% 掉到 73.9%；MbV2-RD 保持跨 patch 依赖，训练方式仍是普通逐层 forward/backward，因此在这组实验里保住了分类和检测表现。所谓 inference invariant，是说推理输出保持与常规网络一致的性质；非重叠切块会打破它。RNNPool 同样减少内存，却有更低指标和 3.2× 训练时间。论文并不是没想到“彻底不重算”，而是这种做法要付出信息传播或复杂数据流的代价。

Figure 9：搜索自动找到的结构有什么规律

Figure 9 展示一个 VWW 网络结构实例。它的目的不是宣布一套固定设计规则，而是让读者看看 joint search 选出的网络在 patch/per-layer 分界两侧有什么模式。

  • 图例说明颜色表示 kernel size；每个 block 的高度表示 expansion ratio；MB{ratio} {kernel}×{kernel} 是命名格式；虚线边框表示 stride=2；底部的 160×160、80×80 等表示 feature-map 分辨率。加一条竖线标出 per-patch 与 per-layer 的切换位置，有助于读者把结构图连回 (n)。

作者从搜索结果观察到：patch 前段多用 1×1、3×3 小 kernel 来减小 RF 和空间重叠；刚进入 per-layer 的中段可能用小 expansion ratio 降峰值；后段用更大的 expansion ratio 提升能力；大 expansion 与大 kernel 很少同时出现，以控制计算和 latency；VWW 对分辨率敏感，因此搜索保留较高分辨率。这些是该任务和搜索空间中观察到的模式，不是所有 MCU 网络都必须遵循的经验法则。

这篇论文到底贡献了什么

读 Related Work 和 Conclusion 时，我会把贡献说成三个层次：

  1. 核心运行时方法： 对前段高内存区域做 patch-by-patch、跨层推理，让高分辨率中间 activation 不必整张同时物化。
  2. 代价缓解： 输入 halo 导致重叠计算，作者重分配前后段的感受野，减少被多个 patch 重复执行的计算。
  3. 适配不同任务和预算： 把网络结构变量与调度参数 ((p,n)) 一起放进 joint NAS，在给定 SRAM、Flash、latency 约束下搜索高精度候选。

所以学长说要重点讲运行时是对的：先讲清 patch scheduling 改变了怎样的实际推理行为，再说明 RF redistribution 和 NAS 为什么围绕它服务。只说“整合了很多已有方案”会淡化论文中心；只说“发明了全新网络”又不准确。另一方面，Related Work 里也承认跨层局部计算有过前作，所以不应把逐空间块计算说成历史上第一次出现。更稳妥的贡献描述是：MCUNetV2 以 patch-based inference scheduling 为核心，将其与感受野重分配、架构—调度联合搜索结合，面向 MCU 峰值激活约束取得了较低的重算开销与任务结果。

还有几处数字要按原文口径谨慎说：

  • 解析 Figure 5 使用 224×224、int8、4×4 patch；板端 Figure 6 在 STM32F746 受 SRAM/Flash 限制时缩小了 width 与 resolution，二者不是可以直接相减归因的一组完全相同模型。
  • VWW 的 >90% under 32 kB SRAM 是任务结果，不代表所有 MCU 视觉任务都能以 32 kB 达到同等精度。
  • VOC H7 的正文有 16.7 与摘要/Table 3 的 16.9 差异；表中 68.3−51.4 为 16.9 个百分点。
  • ImageNet 上 H7 的 MCUNetV2 使用 256M MACs，MCUNet int8 是 126M；精度更高的比较不是等 MACs 对照。
  • Figure 2 的最终 PDF 读数 228 与阅读版源图的 288 不一致；不要靠猜测修图或用这个刻度计算新的斜率。

这使我不会把结论讲成“MCUNetV2 什么指标都赢了”。它证明的是：当主要瓶颈来自前段完整 activation 时，改变运行时调度可以降低峰值 SRAM；多出的 overlap 计算需要认真处理；在论文测试的网络、训练、设备和预算下，联合搜索进一步找到精度更高的可行模型。

它适用于什么情况，又不适用于什么情况

如果模型确实被前几层高分辨率 activation 卡住，而且目标运行时允许控制 patch 数据流，那么 MCUNetV2 的思路值得试。若内存已经够用、任务优先低延迟，而 patch 方案会增加重复计算，就不一定值得采用；若峰值主要来自 NPU workspace、DMA buffer 或不支持分块的算子，paper 的 CNN activation 机制也未必对症。

论文主要在 Cortex-M4/M7 MCU 上验证。迁移到 STM32N6570 这类带 NPU 和多块 SRAM 的平台，得先测总 SRAM 中有多少实际可给模型使用、CPU/NPU/DMA 能访问哪些 bank、编译器是否允许控制 patch 执行、中间 tensor 是否需要 layout conversion、哪些算子会 fallback 到 CPU，以及增加的数据搬运与同步成本。MCU 上“装不下完整激活”的动机，不能未经 profile 就搬到另一个架构上。

我完成的是论文机制、附录搜索流程、图表数字和适用边界的学习与核对；没有完成官方代码核查、搜索复现或板端测量。论文里的 1372→172 kB、71.8% Top-1、68.3% mAP 是作者的结果，不是我的实验数据。

总结

我现在会把 MCUNetV2 讲成这样：常规逐层执行会在 CNN 前段同时保留高分辨率输入与输出 activation，造成峰值 SRAM；patch-by-patch scheduling 让前段局部区域跨层计算，降低同时驻留的数据。为了保持卷积边界输出正确，输入 patch 需要带重叠 halo，因而增加重复 MACs。感受野重分配缩小被重复执行的前段 RF，并在后段补回部分感受野；joint NAS 则在部署前一起选择网络与调度参数 ((p,n))，使候选满足资源约束并争取更高准确率。

我从这篇文章里带走的不是“分块一定更快”，而是一套检查顺序：先确认瓶颈属于权重、activation 还是 workspace；再追踪哪些数据在什么时候必须同时存在；接着算出调度改变带来的重叠和计算成本；最后核对图表比较的模型、分辨率、位宽、硬件和指标是否一致。只有这些条件都对上，内存数字才会变成有用的系统结论。
